## Abstract
Automated source-code analysis can help software developers recognize software weaknesses and self-admitted technical debt (SATD). The NLBSE 2027 multitask code classification competition provides a dataset of functions and comments annotated for two binary tasks: weakness detection and SATD/MAT detection. Its official CodeBERT baseline reports F1-scores of 0.939 and 0.881 for the respective tasks, averaging 0.910. We investigate whether relatively simple changes to representation, training and output-threshold calibration can produce a better balance between classification effectiveness and computational expense. Our design compares a low-cost TF-IDF model with a shared-encoder CodeBERT model using the competition's released dataset. We reserve an internal part of the training data for tuning and withhold the public evaluation partition until model choices are finalized. We evaluate each task with precision, recall, F1 and accuracy, then compare their unweighted mean F1, inference time and computational costs. **[TO FILL: state actual evaluated models, sample sizes, measured scores, and whether the stated research question was supported; do not submit an abstract implying experiments that have not run.]**

## 1. Introduction
Source code is often difficult to maintain not only because it may contain mistakes but also because developers face incomplete documentation and historical shortcuts. Some defects create security vulnerabilities, while other issues appear in comments acknowledging shortcuts or future work. A comment such as `FIXME: this workaround is temporary` is an example of a statement that may signal self-admitted technical debt (SATD); such comments are useful evidence, but they are not equivalent to vulnerabilities. A function can have either label, both labels, or neither. This makes detecting both concerns a natural software-maintenance problem and a suitable test of machine learning models that read code and accompanying natural-language annotations.

NLBSE 2027 defines a multitask classification challenge over formatted functions and their comments. Each prediction is a vector `[weakness, MAT]`, in which the two output values are independently binary. The official competition model builds on CodeBERT, a pretrained representation of programming and natural language [1]. The organizers report an F1-score of 0.939 for the weakness output and 0.881 for the MAT output, with unweighted mean F1 0.910 [4]. These results provide an ambitious baseline, especially because the two labels need not be equally common or equally easy to detect.

The topic began with a broader proposal to use artificial intelligence to improve code comments. Research into the current competition clarified that the actual task is classification of code and existing comments rather than generating new comments. We therefore reformulated the project around improving the official classification baseline while retaining the broader goal of studying how AI can interpret useful information in software artifacts. This change creates a direct link between the experimental design and the competition's published dataset and metrics.

Our research questions are: **RQ1:** can a tuned multitask model improve the mean F1-score relative to the organizer-reported CodeBERT baseline? **RQ2:** how does changing output thresholds alter precision and recall for weakness and MAT detection? **RQ3:** what tradeoffs exist between predictive quality and inference cost when comparing a simpler text-based model with CodeBERT? We expect the MAT output to benefit most from controlled threshold selection because its published F1 is lower, but this is an empirical hypothesis rather than a known result.

The intended contribution is a documented and repeatable evaluation that distinguishes reported baseline results from outcomes measured by our team. Because negative findings are informative in empirical software engineering, the study is useful even if none of the attempted modifications beats the baseline. We will report both improvements and failures, along with the methodological and resource limitations that constrain interpretation.

## 2. Related Work
**CodeBERT.** Feng et al. [1] introduced CodeBERT, a pretrained transformer model for representing code and natural-language text. Its learned representations support tasks that involve both programming language and natural language, including code search and documentation generation. The NLBSE organizers use it as the encoder for a two-output classifier [4]. As a result, CodeBERT offers a relevant baseline that incorporates the characteristics of both forms of software text, while potentially requiring more computation than a conventional sparse-text classifier.

**Multiple labels and dataset construction.** Mock et al. [2] introduced MADE-WIC, a collection combining annotations related to weaknesses and technical debt for software functions and comments. The collection was built by combining previous datasets whose annotation choices can differ. This is important for model comparison: even when evaluation metrics are computed correctly, labels may represent imperfect or mixed definitions of the phenomena being detected. NLBSE 2027 derives its benchmark from MADE-WIC and further formats, filters and splits examples for use in the competition [4].

**Multitask learning for vulnerabilities and SATD.** Russo, Melegati and Mock [3] investigated whether a model jointly trained on vulnerability and SATD labels could benefit from connections between the two tasks. Their reported experiments did not find significant improvements of multitask approaches over compared single-task configurations, including weighted-loss variants. This is a useful caution: joint training should not be assumed to improve performance automatically. Our work tests a specific shared-representation approach and emphasizes independent task-level measures rather than treating both labels as a single undifferentiated result.

**Relation to our work.** Unlike a new dataset paper, our study builds on the released NLBSE benchmark. Rather than assuming large generative models necessarily improve the target task, we compare a simpler sparse-text representation against a CodeBERT-based model and study how threshold choices change the usefulness of two simultaneous predictions. The distinctive element is not a claim of inventing a new neural architecture; it is a controlled, transparent comparison grounded in the official competition and informed by software engineering concerns about cost, correctness, and replication.

## 3. Method
### 3.1 Dataset and labels
The organizer repository describes 214,586 publicly available training functions, 30,655 publicly available evaluation functions (named `test` on Hugging Face), and 61,311 hidden examples reserved for the competition's final ranking [4]. The official dataset comes from sources including OSPR, Big-Vul and Devign within MADE-WIC. The repository documents normalization using `clang-format`, token-length filtering and jointly stratified splitting. Each record includes `Projectname`, `Filepath`, `Function` and `Label`. The input is the formatted `Function` string; the target vector is `Label = [weakness, MAT]`.

We plan to use all released training examples for fitting the final comparison. During development, we split only the public training set into model-fitting and internal-validation subsets, allocating approximately 85% to fitting and 15% to validation using a fixed seed (42). We stratify on joint combinations of the two labels when sufficient examples of each combination exist. The public `test` split is not used for prompt or feature selection, threshold calibration, stopping decisions, or hyperparameter tuning. A final evaluation on that split is conducted only after the method is frozen. Organizers do not release their hidden competition test labels.

### 3.2 Preprocessing
The dataset already contains normalized functions. We retain the entire text field, including any comments embedded in the function, instead of manually deleting the very evidence needed for MAT classification. We verify that binary labels have exactly two entries and confirm the order on every training/evaluation path. The TF-IDF representation uses character n-grams of lengths three through five, with sublinear term frequency and a capped vocabulary, retaining information about short code tokens, punctuation and words in comments. For CodeBERT, we use the model's existing tokenizer and truncate functions to a configurable maximum token length (256 in the proposed default run). Truncation can hide later comments or code statements; we therefore record the chosen maximum length and recommend an optional ablation of 128, 256 and 512 tokens.

### 3.3 Models
**E0: Published CodeBERT baseline.** The organizer reports a CodeBERT encoder shared by the two tasks and a two-output classification head. We use its published F1-scores as an external point of comparison. We must reproduce the baseline under comparable conditions, or explicitly disclose that it remains a published comparison rather than our controlled measurement.

**E1: Low-cost TF-IDF comparison.** A single preprocessing pipeline transforms code text into one sparse TF-IDF feature space. A multioutput logistic model fits one binary head for weakness and one for MAT on these shared features. This constitutes a practical shared-representation baseline, but does not jointly optimize both heads through a neural representation; we will not mislabel it as a joint-backpropagation multitask transformer. Class-balanced logistic regression is used to address uneven label frequencies. This model tests whether a much less computationally expensive approach can still be competitive.

**E2: AI-based multitask CodeBERT.** We use `microsoft/codebert-base` with a classification head producing two logits. Because both labels may be true at once, the model uses independent sigmoid outputs with binary cross-entropy (configured through the transformer's multilabel-classification setting), rather than a two-way softmax. Both outputs share an encoder, making this one jointly trained neural model. The preliminary training configuration is two epochs, learning rate 2×10⁻⁵, batch size eight and a maximum sequence length of 256 tokens. These are planned defaults rather than tuned optima; any deviation must be logged alongside performance.

### 3.4 Threshold tuning
For each label, we convert the model's probability to a 0/1 prediction by comparing it to an independently selected threshold. We evaluate thresholds between 0.10 and 0.90 in steps of 0.05 using only internal validation examples. The threshold maximizing that label's validation F1 becomes fixed for later public evaluation. This can improve sensitivity to MAT without forcing the same decision rule on weakness predictions. We will also report whether improvement in recall came at the cost of reduced precision. The public evaluation set must not be used to choose thresholds.

### 3.5 Metrics and computational resources
For each output, we calculate precision, recall, F1-score and accuracy. The main predictive metric is the arithmetic mean of the weakness and MAT F1-scores, matching the organizer's stated objective. Where appropriate, we record the counts of true positives, false positives, true negatives and false negatives. We also log average inference seconds per function, hardware, batch size, peak memory and model size. The organizer's overall competition formula weights mean F1 at 60%, average execution time at 20% and GFLOPs at 20% [4]. We will rely on the official competition notebook to obtain an organizer-comparable cost measurement rather than inventing GFLOPs from the training code.

### 3.6 Reproducibility and validity safeguards
We fix random seeds, publish preprocessing and training code, and provide dependencies and step-by-step commands. The artifact should record exact library versions, hardware details and final checkpoints. We also plan to inspect duplicate or near-duplicate functions across training/evaluation partitions, label imbalance by project, and examples of false positive/negative predictions. We will not assume that one run establishes a statistically reliable advantage; time permitting, we will repeat full experiments with three seeds and report variability. If limited compute forces fewer runs, we will say so explicitly.

## 5. Discussion
Our evaluation is designed to distinguish between improving classification quality and improving efficiency. If threshold tuning increases MAT recall, that may be useful for surfacing more known technical-debt comments, but additional false positives would increase the review burden on developers. Likewise, a model with high aggregate F1 can miss important vulnerable functions. For security-sensitive applications, recall and false-negative counts must be interpreted alongside F1 rather than hidden inside one score.

A lightweight classifier may be much easier to run locally, but training on character patterns alone may be insufficient to understand program behavior. Conversely, a CodeBERT-based model can use learned context from code and natural language while requiring more memory and processing time. The best engineering choice depends on both predictive effectiveness and deployment constraints. The competition explicitly evaluates cost, supporting this broader view. **[TO FILL: discuss the tradeoff actually observed, with quantitative values.]**

There are several threats to validity. First, labels are inherited from datasets whose annotation techniques and coverage may vary [2]. Second, some functions may overlap or share project-specific patterns, possibly inflating the apparent ability to generalize. Third, functions truncated for transformer training may lose crucial evidence. Fourth, our comparison can be unfair if the official baseline and new models use different hardware or evaluation procedures. Fifth, tuning too many variants against a single public evaluation partition would give an overly optimistic result. Our internal validation split and final-use-only public evaluation policy attempt to reduce this risk. **[TO FILL: explain which threats were audited, with actual counts if available.]**

Prior work found no significant improvement for some multitask-learning configurations [3], so a negative result should not be treated as a failed project. If our models do not exceed the baseline, the result can still clarify whether simple sparse text, default multitask CodeBERT or probability calibration is a realistic route for improvement under constrained resources. **[TO FILL: state actual supported conclusion.]**

## 7. Future Work
Future experiments could test class-weighted loss, alternative encoders, longer context windows and comment-aware representations to determine which features most affect MAT prediction. Model calibration beyond grid-search thresholds may improve reliability. A repeated-seed study or cross-project evaluation could clarify whether improvements survive changes in random splits and project domains. Larger evaluations could also investigate how model confidence, compute cost and false-negative risk should be balanced for deployment in real code review workflows. Finally, the original code-comment generation proposal could become a distinct, complementary study of the factual accuracy of LLM-written documentation, with a separate annotation protocol and benchmark; it should not be conflated with the present classification results.
